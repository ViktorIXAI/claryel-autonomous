## Bank finding: `C-ex6-02` is a bank defect, not a contour target

The chronic C stable-fail (`want=['C']`, model answers `A,C,D` / `C,D` / `A,B,C,D` on 0/12 rows across
the six-seed map and pair-239) fails because the **gold is over-narrow**. The task asks «какой вариант
печатает [1, 2, 3]?» over snippets A–D, and executing the bank's own text shows A
(`sorted({3,2,1,1})`), C and D all deterministically produce `[1, 2, 3]` (B also evaluates to
`[1, 2, 3]` under CPython but its set iteration order is language-unspecified, so excluding B is
intentional — excluding A and D is not). The model is semantically right on A and D; no contour
mechanism can or should chase this cell. Logged for the owner per the inbox doctrine (bank changes are
owner-commanded, like the `K` value-shape and `B-ex6-04` defects). Group 1's remaining live cells
(`C-ex6-00/01/03`) are content lotteries, identical failure bytes in both arms on their losing seeds.
