# P3032 onboarding — driver, swap, power cap, AVX1 engine build (2026-11-02)

Contract: bring a cold-spare HP box (Xeon E3-1270 v2, RTX 3060 12 GB, 31.5 GiB
DDR3) into the Strata fleet; keep the display on the legacy GPU with the RTX
3060 fully free for inference; cap the GPU at 150 W; IQ3_S from the fleet seed;
first context ladder to 32k. Speed table:
results/p3032-iq3s-context-ladder.md.

## Exact configuration applied

- NVIDIA driver 580.178.04 installed headless-style: `options nvidia-drm
  modeset=0` in a modprobe drop-in; text console owned by the legacy GPU via a
  small systemd unit (unbind `simple-framebuffer`, bind `vtcon1` at boot).
  After reboot: console on legacy card, `nvidia-smi` healthy, 12 GB free.
- Swap: boot-SSD 8 GB swapfile removed; 64 GB swapfile created on the NVMe
  data disk, mounted via fstab.
- Power: `nvidia-smi -pm 1 && nvidia-smi -pl 150` applied live and re-applied
  at every boot (user cron). Measured never exceeds ~149.8 W under load.
- Same day, A/B test: cap removed for one ladder pass (factory max 187 W).
  MAINTAINER NOTE: removal was explicitly short-term — the box's PSU/power
  cable cannot sustain the card's peak (177.4 W observed). Cap restored
  immediately after the pass and is the standing state; removing it again
  requires operator hardware changes. Envelope comparison:
  results/p3032-iq3s-power-envelope.md (prefill cap-independent; warm decode
  +10-24 % for +28 W peak — not worth the electrical risk).
- Model IQ3_S (78 GB + packs + mtp) pulled over LAN from the fleet seed box
  with a dedicated pull key; rsync at ~90 MB/s, ~15 min, markers `.done` 2/2.
- Serve config: fleet P2005 production template re-scaled for this box —
  `--prefill 4096 --max-context 32768 --pool-workers 6 --resident-experts
  --resident-budget-gib 16 --conversation-cache-mib 512
  --conversation-cache-min-free-mib 2048 --memory-limit-mib 19456`, vision
  block removed. Sanitized copy:
  hardware/configurations/strata-iq3_s-p3032.launch.json.
- Watchdog (`keep-up`) re-installed only after the working engine booted;
  during the crash-loop below it was deliberately disabled.

## Failed build round 1 (published per fleet build rule)

Stock prebuilt engine 0.1.55 refuses to start on this CPU: **AVX2 required**,
Ivy Bridge lacks it. First local-build attempt (`-DSTRATA_ISA_FLOOR=avx`,
`-DCMAKE_CUDA_ARCHITECTURES=86`) with the distro CUDA toolkit (nvcc 12.0)
configured fine but failed compiling the fused CUDA prefill kernel
(`src/prefill/moe_fused_iq.cu.o`, distro nvcc):

```text
Error: Formal parameter space overflowed (4216 bytes required,
max 4096 bytes allowed) in function ...native_kernel<16,true,2,2,256,true>...
```

Diagnosis: this engine's fused IQ kernel passes more by-value parameters than
the 4 KB kernel-parameter space of the 12.0-era ptxas; CUDA 12.6 raised that
limit.
Raw log stays on the workstation (322 KB, sha256/16 `7a70d58def37131a`).

## Successful build round 2

Installed CUDA 12.6 dev components (nvcc, cudart-dev, libraries-dev, cccl)
from the NVIDIA apt repo, reconfigured:

```text
cmake -G Ninja -S repo -B build-avx \
  -DSTRATA_ENABLE_CUDA=ON -DSTRATA_BUILD_TESTS=OFF \
  -DSTRATA_Q6K_EXPERTS=ON -DSTRATA_MMQ_KQUANTS=ON \
  -DCMAKE_CUDA_ARCHITECTURES=86 -DCMAKE_BUILD_TYPE=Release \
  -DSTRATA_ISA_FLOOR=avx \
  -DCMAKE_CUDA_COMPILER=/usr/local/cuda-12.6/bin/nvcc \
  -DCUDAToolkit_ROOT=/usr/local/cuda-12.6
ninja -C build-avx
```

Result `BUILD_DONE: strata 0.1.55`; staged with `BUILD.json`. CPU kernels then
run on the AVX1 128-bit path (engine prints
`expert kernels run AVX1 128-bit (iq_avx1, older-CPU build)`), GPU kernels on
sm_86. Server boots clean: `resident RAM mode: experts 16 GiB in RAM
(page-locked)`, `file tier reads unbuffered`, swap usage ≤ 0.5 MiB under load,
min 9.0 GiB RAM available (headroom rule satisfied).

## Failures observed and kept as evidence

- Crash-loop of the stock engine before diagnosis (watchdog disabled).
- A first ladder draft wasted a pass: a shared probe text silently hit the
  engine prompt cache, so "cold" rows showed ~full cache reuse; and one rung
  sized to ~44k tokens returned **HTTP 400** over ctx 32768 — logged as a
  capacity rejection (raw pass-2 log, sha256/16 `a5c8a394e2944529`).
- Both fixed in the final pass (unique salted rungs, calibrated 31.1 tok per
  pad sentence).

## GPU compatibility note (2026-11-03)

Tesla P100 probe failure on this box (NVRM "BAR1 is 0M @ 0x0") is an
aperture problem: the card's default Compute mode requests a 16 GiB BAR1,
while the Z220 BIOS exposes only a 512 MB sub-4G MMIO window
(TOLM=0xE0000000, locked) and its root-port 64-bit apertures read zero and
ignore writes. No ReBAR capability on the card. Firmware GPU-mode was
switched to Graphics (256 MB BAR1) on P1005 — see P1005 CHG-003 and
`results/p100-gpumode-256mb-bar1.md`. Validation on this box is pending
physical re-install; on first successful probe, apply the 150 W power limit
immediately (PSU/cable constraint on record above).

## Back on the wire after ten days dark; console identity confirmed, SSH listener absent (2026-11-13, open)

**Observation.** After being unreachable in every nightly OS audit since 2026-11-03,
the box answered the wire the same day the maintainer reported link lights at the
router: ICMP replies at ~0.35 ms with TTL 64 (same-segment, wired path), neighbour
entry resolves, and the wired NIC MAC sits in an HP-allocated OUI block, which is
what HP ships on this board's integrated Intel 82579LM. Identity is triple-confirmed
without guessing: the console photograph shows the `p3032 login:` prompt, the router's
own client table lists the device under that name as a wired HP device, and the NIC
OUI matches the board.

**What is not reachable.** Every probed TCP port is closed, and port 22 answers
`connection refused` rather than timing out — the listener is absent, not firewalled.
So the machine is up, on the wire, and has no SSH server running. Fleet rule applies:
key delivery by inline paste at the console, not over HTTP (the control host's
default-deny inbound drops the key port; the check-in/key endpoint was moved to the
always-on inference host and verified from a second LAN box the same day).

**Console photograph read.** Ubuntu 24.04.4 reached its text login prompt, so this is
not a kernel hang: the two `acpi_call: Cannot get handle: Error: AE_BAD_PARAMETER`
lines are printed by the `acpi_call` dkms module *after* the prompt is up. On this
board that failure is expected noise — the ACPI method the module probes is not
present/manageable here, the same reason the chassis fan headers cannot be driven
from Linux (see the GPU fit rule). ACPI method noise is not evidence about NVMe or
PCIe health, and nothing in the frame supports an ACPI-driven freeze. No `acpi=off`,
no BIOS ACPI toggles: unproven and it would take the thermal/fan story down with it.

**Storage/slot facts for this board** (HP Z220 CMT QuickSpecs DA-14286, and the
installed BIOS): one PCIe Gen3 x16 slot (electrical x16) — the graphics slot; HP
supports only After-Market-Option-certified cards in it when it does not hold
graphics. One Gen2 x4 in an x16 connector (full length). One Gen2 x4 in an
open-ended x8 connector — a full-length card seats but the slot supports half-length
cards only. Two Gen2 x1, two 5 V PCI. There is no M.2 on the board, and this BIOS
generation has no NVMe boot path: an adapter NVMe is a data-tier device and the boot
device stays SATA. Passive M.2-to-x16-connector risers are not supported on this
platform at all. The measured per-slot ceilings: ~1.6 GB/s (Gen3 x4), ~0.8 GB/s
(Gen2 x4), ~0.2 GB/s (x1) — so on any PCIe path here the drive is PCIe-limited, not
drive-limited, while the board's own 6 Gb/s SATA port has headroom.

**Next (blocked on console access).** After the inline-key console block: read the
kernel journal for the real error set (`nvme`, `pcie`, AER, `link is down`, reset,
timeout), re-measure the NVMe link width/speed and SMART, confirm which card is in
which slot, then seed the hardware fingerprint (this box has been missing from the
fingerprint roster since 03.11), add the wake-address record and the audit roster
entry, and re-run the inference ladder only after the disk verdict is known.

## Maintainer reinstalled to Ubuntu Server 24.04, adapter NVMe gone, box re-onboarded then powered off (2026-11-14, closed for today)

**Access restored the fleet way.** Key pasted inline at the console (no HTTP fetch), sudoers drop-in,
`sshd` enabled. Verified from the control host rather than trusted: login returns hostname `p3032` and
passwordless sudo answers `yes`.

**Bus read after the reinstall.** Zero NVMe devices on the PCI bus — the FireCuda and its adapter are
physically out of the machine. `dmesg` shows **no** BAR-allocation failures and no AER/link errors at
all; the only PCIe notes are the platform's own: FADT declares no PCIe ASPM support (so the kernel
disables it) and `_OSC` hands AER/PCIe capability control to the OS. So the earlier failed-allocation /
freeze symptom left the machine together with the adapter.

**GPU is not the card in the passport.** The bus carries GA107 (`RTX 3050 8 GB`) on the Gen3 root port,
link trained to **8.0 GT/s x8**. That is the card's own electrical width, not a slot fault: GA107 boards
are x8, so on this board the pairing is as good as it gets. No vendor driver is installed on the fresh
OS, so nothing is serving yet.

**Storage as installed now.** Root on the SATA SSD (5 % used), data on a SATA HDD (WD10EZEX 931.5 GB,
914 GB free), 8 GB swapfile back on the boot SSD. The old layout — adapter NVMe holding the data tree
plus a 64 GB swapfile — is gone.

**Freeze story, status.** The hangs were observed in the old configuration (adapter NVMe carrying the
data tree plus a 64 GB swapfile on it). With the adapter out and swap on the SSD the box survived the
whole install and an orderly power-off — that is consistent with the old layout being the trigger but it
is **not a measured root cause**: no kernel journal from a hanging boot was captured, because every
hang ended in a power cycle before anything could be read. Standing rule for this board while that stays
unproven: an adapter NVMe here is a data-tier device only — never the boot device, never the swap
carrier. If the adapter comes back, capture `journalctl -k -b` and the SMART/link state before putting
anything on it.

**What blocks fleet work now.** Netplan comes from `cloud-init` and runs **DHCP**, so the box's address
is not stable and has already moved once; the nightly audit, the fingerprint roster and the wake record
all need a stable address or a MAC-based discovery step (the check-in collector on the inference host
reports hostname + MAC, which is enough to re-find it after each lease change).

**Power state.** Powered off cleanly at the maintainer's request (`systemctl poweroff`), verified by
losing ping and seeing the neighbour entry decay. Bring-up order when it returns: pin the address →
vendor driver → engine build (the board has no AVX2, the historical engine needed a local build with
`STRATA_ISA_FLOOR=avx`) → fingerprint seed → audit roster.

Data in this record and the linked results file is safe to publish (no
secrets, addresses, or local paths; raw logs stay on the workstation, sha-pinned in logs/INDEX.md).

## Rebuilt as an inference box: NVMe wiped and repartitioned, vendor driver, engine build, model seed, autostart (2026-11-14, open)

**Disk work, on the maintainer's instruction.** The NVMe that came back with the machine is a
**WD PC SN740 256 GB** (serial pinned before anything was touched; the old FireCuda 530R is gone).
It arrived holding a stale Ubuntu clone — a 1 GB vfat plus a 237 GB ext4 copy of the same layout the
boot SSD carries — which is exactly the kind of duplicate EFI copy that makes a BIOS pick the wrong
disk. Sequence: NVMe crypto-erase (`format --ses=1`), zero the header and the trailing 32 MiB,
`wipefs`, `sgdisk --zap-all`, then a fresh GPT:

| partition | size | type | use |
|---|---|---|---|
| `p1` | 32 GiB | swap (0x8200), LABEL `SWAP32` | swap, prio 0 |
| `p2` | 206 GB | Linux filesystem (0x8300), LABEL `AI`, ext4 | mounted `/ai` — model, packs, engine |

The installer's 8 GB swapfile on the boot SSD was swapped off, removed from `fstab` and deleted;
`vm.swappiness=10`. The disk is now **not bootable** (no EFI partition on it) and the boot order keeps
the SATA SSD first. `fstab` uses UUIDs with `nofail` for `/ai`, so a missing adapter cannot hang the
boot again. The archive tier stays where the maintainer put it: the 1 TB WD HDD at `/a` (XFS) was left
untouched, and the boot SSD keeps only the system.

**Where the NVMe actually sits** (measured, not assumed): bus `02:00.0` under the chipset downstream
port `00:1c.0`, link **5 GT/s x4** = Gen2 x4 — a chipset port, not the CPU-attached Gen3 x16. The
drive itself is Gen3 x4, so this board caps it near 2 GB/s theoretical. Its BAR0 is a plain 16 KB
sub-4G region and `dmesg` shows no allocation failure, no AER, no reset loop: the aperture/BAR story
from the Tesla P100 probe does not repeat with this drive in this slot.

**GPU.** `GA107 [RTX 3050 8 GB]` in the Gen3 x16 slot, link trained **x8** (the card's own electrical
width, not a slot fault). Driver **580.178.04** from the Ubuntu archive; `nouveau` blacklisted with an
initramfs rebuild — until then nouveau owned the device and the vendor module refused to probe
(`NVRM: GPU 0000:01:00.0 is already bound to nouveau`). After the reboot: `nvidia-smi` clean,
8192 MiB, 30 °C idle, reported power limit 115 W. No cap applied: this card sits well under the 150 W
envelope the previous RTX 3060 needed on this PSU.

**Engine.** The prebuilt binary still will not run on this CPU (AVX2 floor), and the newest release
line builds for compute capability 12.0 only, so the box stays on the **Strata v0.2.10** line, built
locally: CUDA 12.6 nvcc from the NVIDIA apt repo, `-DSTRATA_ISA_FLOOR=avx`,
`-DCMAKE_CUDA_ARCHITECTURES=86`, `STRATA_Q6K_EXPERTS=ON`, `STRATA_MMQ_KQUANTS=ON`. Source synced from
the fleet build host (6.1 GB), built in `/ai/strata/build-avx`.

**Model.** IQ3_S (78 GB) + pack (1.5 GB) + MTP (787 MB) pulled over LAN from the fleet seed host at
~110 MB/s into `/ai/strata/...`. Serve config taken from the same-class 8 GB host (the Arc A750 box)
and re-scaled with this box's proven resident-expert settings: `--max-context 32768 --kv int8
--prefill 4096 --spec 4 --mtp --resident-experts --resident-budget-gib 16 --memory-limit-mib 19456
--vram-reserve-mib 300 --pool-workers 6`. Autostart is a systemd **system** unit (`Restart=on-failure`,
`LimitMEMLOCK=infinity`, `STRATA_UNBUFFERED_LOAD=1`, nvidia persistence in `ExecStartPre`) — no cron
watchdog, no dependency on a logged-in session.

**Model seed route (recorded so it is not reinvented).** The fleet build host cannot be reached from

## IQ3_S on the RTX 3050 8 GB: what 8 GiB of VRAM actually buys, plus slot audit (2026-11-14, open)

**Engine.** v0.2.13.1 cloned from upstream and built here (`-DSTRATA_ISA_FLOOR=avx`,
`-DCMAKE_CUDA_ARCHITECTURES=86`, CUDA 12.6): `/ai/strata/build-0213/strata`, 141 MB, `BUILD_RC=0`.
Basalt v0.3.3 is not an option on this card — its CMake guard asks for compute capability 12.0
(Blackwell) and CUDA 13.

**Decode ladder, same model (IQ3_S), 700-token probes.**

| profile | ctx | KV | RAM arena | draft | VRAM expert cache | hit | tok/s |
|---|---|---|---|---|---|---|---|
| V1 P1006-style + arena 16 | 32768 | int8 | 16 GiB | spec4+MTP | 1.58 GiB / 821 slots | 36-49 % | 5.2-5.9 |
| V2 arena 21, reserve 700 | 32768 | q4_0 | 21 GiB | spec4+MTP | smaller (KV+guard) | - | 3.9-4.1 |
| V3 no arena (P1006 shape) | 32768 | q4_0 | none | spec4+MTP | 1.56 GiB | - | 4.4 |
| V4b small ctx, no arena | 8192 | q4_0 | none | spec4+MTP | not captured | ~50 % | 7.6-8.2 |
| V5 arena 16 again | 8192 | q4_0 | 16 GiB | spec4+MTP | not captured | 57-65 % | 4.8 |
| **V6 standing** | **4096** | **q4_0** | **none** | **spec 2, no MTP** | **2.74 GiB / 1422 slots** | **72-80 %** | **9.5-9.7** |

Reading of the table: the expert set is **45.25 GiB** and the card can hold **2.7 GiB** of it, so the
run is a streaming problem, not a compute problem. Every GiB moved out of KV, the MTP draft head
(812 MiB) and the driver reserve goes straight into the expert cache and comes back as decode speed:
1.56 GiB -> 2.74 GiB took the box from 4.4 to 9.5 tok/s. A RAM arena makes it *worse* on this box (V5 < V4b), and the cause is RAM **capacity**, not the CPU:
the same card and model on the 62 GiB host with the whole 46.47 GiB expert set page-locked runs
23-26 tok/s. With 31.5 GiB only half the experts can be pinned, so a partial arena pays for the pinned
half and still misses into the file tier; 21 GiB pushed the engine into CPU-share and shrank the prompt
chunk 4096 -> 1024, 24 GiB died.

**Canonical suite.** `standard-v1` stopped at 17/22 by choice (the bottleneck was already proven):
generation 5.1-5.9 tok/s on short/4k/16k, prefill 116-125 tok/s, first token on 16k prompt 132 s.

**Card health (raw CUDA micro-benchmark, nvcc sm_86, engine stopped).** FP32 FMA **8232 GFLOP/s**
= 88 % of the GA107 theoretical 9.3 TFLOP/s; device-to-device copy **207 GB/s** = 92 % of the 128-bit
7001 MHz theoretical 224 GB/s; PCIe **6.5 GB/s H2D / 6.6 GB/s D2H** = the card's own x8 Gen3. SM clock
1822 MHz, 20 SMs, 7.7 GiB visible. The card is healthy and not throttled; its *capacity* is the limit.

**Disk tier (direct I/O, caches dropped, engine stopped).** Sequential 1 GiB **1.3 GB/s**; 24 x 4 MiB
random **1175 MB/s**; 200 x 128 KiB random **92 MB/s** (weak small-read tail of a DRAM-less drive, not
this workload's operating point). The pack's expert blob / VRAM cache slot is **1.97 MiB**
(2.74 GiB / 1422 slots = 1.58 GiB / 821 slots), so the 4 MiB random figure is the relevant one.
During a 700-token probe the engine counted **41.4 GB read from storage** ("0 major faults", mmap reads
of the GGUF in place) = **~560 MB/s sustained, ~59 MB of SSD reads per generated token** — decode here
is a disk-streaming problem at the drive's measured ceiling for 2 MiB reads. Link: the drive (WD PC
SN740, DRAM-less) is capable of Gen4 x4 but trains **Gen2 x4**, which is the ceiling of the chipset
root port `00:1c.0` (C216).

**Slot audit against the HP service manual (the maintainer asked whether the cards are in the wrong
slots).** Z220 CMT has one **PCIe 3.0 x16 on the CPU**, one **PCIe 2.0 x4 in an x16-length connector**
and one **PCIe 2.0 x4 in an x8-length connector** (both chipset), plus 2 x x1 and 2 x PCI. Live bus:
GPU on root port `00:01.0` = the CPU Gen3 x16 slot (correct, and the only one), trained **x8** because
the 3050 is an x8 card — no slot change can give it more lanes. NVMe on `00:1c.0` = a chipset port,
Gen2 x4 is the platform maximum; `LnkSta: 2.5 GT/s` while idle is link power management, the measured
6.5 GB/s under traffic proves the GPU link runs Gen3 x8. Nothing is misplugged: PCIe bandwidth is not
the constraint (expert streaming needs ~0.5-0.6 GB/s, ten times under the link).

**What changes when the card is swapped.** The fix is VRAM capacity, not slots: the same board with an
RTX 3060 12 GB and Strata 0.1.55 previously measured 37-43 tok/s on IQ3_S because ~6-8 GiB of experts
fit. An x8 Gen3 link (which is what every candidate card will use here) is enough.

**Standing config now in `/ai/strata/launch/iq3_s-32k.json`** (file name kept for continuity):
`--max-context 4096 --kv q4_0 --vram-reserve-mib 200 --spec 2`, no `--mtp`, no resident/arena flags,
expert cache auto. RAM sits at 28 GiB used of 31.5 with the model mapped through the page cache and
swap untouched.

**Still open:** autostart (system unit not installed — waiting for maintainer consent), and the
16k-prompt prefill path, which is memory-bound and still 130 s for a 16k prompt.
